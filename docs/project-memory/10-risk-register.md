| R-001 | `operatorSession`'s cookie is `Secure` (05-api-contracts.md), but no session has given the project a real TLS termination story — `docker-compose.yml` serves `backend`/`frontend` over plain HTTP. A real browser will never store the cookie in that deployment shape, so login would appear to succeed but the dashboard would never actually stay authenticated. | Security / Deployment | High — the real operator-facing product is unusable as currently deployable. This is not an ordinary deployment risk sitting alongside the rest of this register: pulsewatch's stated premise (`00-project-brief.md`) is being a genuinely *operable*, continuously-run system — not a demo that merely compiles and passes tests, but something that could actually run as a real operator-facing product. A cookie that can never actually be secure in the only deployment shape the project currently has isn't a peripheral gap; it means the operator-facing half of the product, as it stands, cannot honestly be called operable at all. That is a gap in pulsewatch's own central thesis, not a routine ops risk — the same kind of explicit severity statement `lexicon`'s ADR-0004 gave its own permanently-descoped LLM credentials. | Certain, if deployed as-is | None yet — Session 9 verified the dashboard flow only via a temporary, torn-down self-signed HTTPS harness (see `12-session-handoff.md`), not a real fix. A future deployment-focused session needs to add a real reverse proxy/TLS termination (e.g. Caddy with a real or Let's Encrypt cert) to `docker-compose.yml` and document it in `08-deployment-and-operations.md`. | Open | Session 10 |
