| R-005 | **Opened Session 12; root cause refined mid-session after a second occurrence.** Several packages' test fixtures (`scheduler`, `agentapi`, `alerting`, and `operatorapi`'s pre-Session-12 tests, plus Session 12's own new ones) clean up a test-created `targets` row with a best-effort `DELETE FROM targets` that silently swallows the error when it fails — and it does fail whenever `check_results`/`incidents`/`check_rollups_hourly` rows still reference that target (all use a plain `REFERENCES`, deliberately not `ON DELETE CASCADE` — real historical data shouldn't silently vanish if a target is ever hard-deleted). The `check_results`/`incidents` half was already an accepted trade-off per `alerting/testdb_test.go`'s own comment, predating this session. **What Session 12 found that wasn't previously documented:** this project's own live `pulsewatch-backend-1` container runs its real scheduler continuously against the same real local Postgres a developer's `go test ./...` also runs against — its 1-second tick picks up *any* newly-inserted `targets` row with `agent_id IS NULL` (regardless of which test or package created it, even ones that never call check-execution code themselves, like the `/status`/`/slo`/CRUD tests) and executes a real check against it within about a second, writing real `check_results` — so essentially *any* local test that creates a target row is exposed, not only the packages whose own tests explicitly exercise check execution. Session 12's own test runs left 78, then a further 23, then a further 4 orphaned test-fixture targets in the real, live database (three separate occurrences across one session), visible on the real operator dashboard alongside genuine data, each time found and deleted (see `12-session-handoff.md`). Session 12's own new `check_rollups_hourly` call sites (`internal/rollup`, `operatorapi/slo_test.go`) were given "delete child rows before the target row" cleanup, which reduces but does not eliminate the exposure — a live scheduler tick can still land in the small window between a test's own cleanup steps (they are three separate, non-transactional `Exec` calls). The broader, pre-existing gap across the other packages was not fixed (out of scope for Session 12's bounded SLO/rollup objective). **Recurred repeatedly in Session 13** during Part 3's flake-reproduction work (5 isolated `scheduler` reruns, then two separate full `go test ./...` batches): orphaned rows peaked at 74 and 43 in two of the cleanup episodes (on top of the real 4), each found, named, and cleaned up transactionally (child rows before target row, in one `BEGIN`/`COMMIT`) before proceeding, re-verified back to exactly 4 real rows each time — confirming this is not a one-off, still fully open, and still exactly the mechanism described above. | Testing / local-dev hygiene | Low — never reaches CI (ephemeral Postgres, no live backend container sharing it) or production (test fixtures only); only pollutes a developer's own long-lived local `docker-compose` instance | Certain, on every local `go test ./...` run against a persistent local Postgres that also has this project's own live backend container running its scheduler | None yet. A future session should either (a) stop the local `backend` container (or at least its scheduler) before running tests locally against the persistent stack, (b) wrap each test fixture's cleanup (child-row deletes + target delete) in a single transaction to shrink the race window, and/or (c) give every package's target-fixture cleanup the same child-rows-first ordering Session 12 applied to its own two new call sites. | Open | Session 14 |

| R-006 | **Opened Session 13.** The originally-reported symptom ("the rollup job appears to have silently stopped ticking" — only 2-3 `rollup job run complete` lines across ~20h of container uptime, no error, no crash, no restart, `docker inspect`'s `StartedAt` constant) was investigated and root-caused: it is **not** a defect in `rollup.Run`'s ticker loop. Cross-correlating logs across three independent containers on this real, live `docker-compose` stack showed *identical* silent gaps at the same wall-clock windows (~17:00–20:00 and ~22:00–10:00, 2026-08-31→09-01) in `pulsewatch-backend-1`'s own HTTP/GIN traffic (all of it, not just rollup logging: 0 GIN lines for entire hours) and in `pulsewatch-postgres-1`'s own log activity — proving the whole container/VM went unscheduled, not that one goroutine died. Confirmed via the WSL2 VM's own `/proc/uptime` (22.28h of real accumulated runtime, less than its wall-clock age) and Windows `Microsoft-Windows-Kernel-Power` event log (sleep/wake pairs on this host, ruled out as the direct cause since each is only seconds long — the actual mechanism is Docker Desktop's own WSL2 VM going idle/unscheduled for extended stretches during host inactivity, not full OS suspend). `time.Ticker` never queues missed ticks, so on resume exactly one catch-up tick fires — matching the observed 3 lines exactly. No data was lost: `RunOnce` recomputes every historical hour-bucket on every tick (Session 12's own self-healing design), so the only real effect is staleness between runs (up to ~13.5h observed) exceeding NFR-005's "fixed hourly cadence." This cannot reproduce on a real always-on deployment (none exists yet — R-003's gate) — it is specific to a dev laptop whose Docker VM idles out. | Testing / local-dev environment characteristic (not a code defect) | Low — no data loss (self-healing recompute), only staleness visibility; would not occur on a real always-on host | Certain on this developer's own local machine whenever the host is idle for an extended period; not applicable to a real always-on deployment | **No code change can force a tick while the process isn't being scheduled at all** — instead, `rollup.Run` (`backend/internal/rollup/rollup.go`) now tracks the real wall-clock gap between consecutive ticks and logs a `WARN` (`"rollup job cadence gap exceeded expected interval"`) whenever it exceeds `TickInterval` by more than 10% — turning a previously-silent staleness window into an observable one. Verified two ways: `TestCadenceGapExceeded` (`cadence_test.go`) unit-tests the threshold logic deterministically (on-time, small jitter, and the real 13h33m observed gap); and a real extended-observation run — `TickInterval` temporarily lowered to 20s, backend rebuilt and redeployed, 9 consecutive real ticks observed over ~3 minutes (14:30:29–14:33:09) at the expected cadence with zero false-positive warnings, then `TickInterval` restored to the real 1h default and redeployed again (confirmed via `git diff` clean and a fresh startup tick in the real logs). | Open (environmental; mitigated with visibility logging, not eliminable) | Session 14 |
| R-007 | **Opened Session 13.** A previously-undocumented flake, separate from R-002: `TestEndToEnd_ThresholdCrossing_DispatchesOnce_ThenResolvesOnRecovery` (`internal/scheduler/alert_lifecycle_test.go`) surfaced during this session's verification work. 5/5 isolated reruns passed cleanly (1.3s–3.4s each). Reproduced twice under real concurrent load against the live, shared local Postgres (with `pulsewatch-backend-1`'s own live scheduler also running against it): once in a plain `go test ./...` run (`alert_lifecycle_test.go:279: condition not met within 15s` — the wait for the "opened" dispatch to be recorded, 17.69s), and once under `go test -p 1 ./...` (`alert_lifecycle_test.go:297: condition not met within 15s` — the later wait for `state == "healthy"` after recovery, 17.60s). **This is not fully explained by R-002's own mechanism**: R-002's hypothesis (cross-package concurrent Postgres load from other test packages running at the same time) is what `-p 1` (serialized packages) reliably avoids — and did avoid, twice, for R-002's own two tests. This flake reproduced even under `-p 1` (1 failure in 3 serialized runs), which serializes only `go test`'s own package binaries and has no effect on the live `pulsewatch-backend-1` container's own concurrent scheduler activity against the identical shared Postgres instance — the more likely real contention source for this specific flake, though not proven beyond the timing correlation. Both observed failures are `waitForCondition`'s generic 15s budget being exceeded at different stages of the same test's lifecycle (initial dispatch, then post-recovery state transition), consistent with a shared root cause (real query/dispatch latency margin under contention) rather than a logic bug in either transition. Not root-caused to a specific query or lock this session — diagnosing further (e.g. isolating whether it's the live backend container's contention specifically, matching R-005's already-confirmed mechanism for `targets` inserts, or something in the dispatch/incident path itself) is left to a future session. | Testing / CI reliability | Low-medium — could mask a real intermittent bug in the alert-dispatch lifecycle, or cause spurious CI failures | Occasional, under real load against a shared Postgres also serving a live backend's own scheduler; not yet observed in isolation | None yet — unlike R-002, `-p 1` is not a confirmed reliable mitigation for this one (it failed under `-p 1` once in 3 runs this session). A future session should investigate whether stopping (or at least quiescing) the live local `pulsewatch-backend-1` container's scheduler before running this test locally removes the flake, which would point at the same class of live-container contention R-005 already documents for `targets` inserts, just manifesting as a timing failure here instead of orphaned rows. | Open | Session 14 |

| R-001 | `operatorSession`'s cookie is `Secure`, but no session had given the project a real TLS termination story — `docker-compose.yml` served `backend`/`frontend` over plain HTTP, so a real browser would never store the cookie. | Security / Deployment | **Genuinely mitigated, with an honestly-named residual trade-off.** Session 10 added a real, persistent `proxy` (Caddy) service to `docker-compose.yml`, terminating HTTPS at `https://localhost:8443` for the browser-facing `frontend` (which no longer publishes any plain-HTTP host port at all) and for direct `/api/*` access to `backend`. The cert is `tls internal` — Caddy's own persistent local CA, not a publicly trusted one; a real browser shows a not-trusted warning, which is the accepted, explicitly-named trade-off for this project's self-hosted/local default (see `08-deployment-and-operations.md`'s "TLS termination" section for the full writeup and the real-domain/Let's Encrypt upgrade path). Verified end-to-end this session via a real TLS handshake (`openssl x509` showing `Issuer: CN=Caddy Local Authority - ECC Intermediate`) and a full `curl` cookie-jar round trip against the actual running `docker compose up` stack: `POST /login` over `https://localhost:8443` → real `Set-Cookie: pulsewatch_session=...; HttpOnly; Secure; SameSite=Strict`; that cookie, replayed in a **separate** subsequent request (not the same connection — proving persistence across a reload, not just an in-flight assumption), rendered the real dashboard; unauthenticated `GET /dashboard` → real `303` to `/login`; `POST /dashboard?/logout` cleared the cookie (`Max-Age=0`) and a following `/dashboard` request redirected to `/login` again. Not "closed" in the sense of no residual gap at all — see R-003/R-004 for the distinct, separately-tracked agent-transport/cross-port gaps this does not cover. | Session 10 (2026-08-31) |
| R-004 | **Found closing out Session 10, opened and closed within Session 11.** `agentapi` and `operatorapi` were registered on the *identical* `gin.Engine`/`http.Server` (`backend/main.go`'s old `setupRouter`), so R-001's TLS work never actually made the plain-HTTP agent port (`8020:8080`) agent-traffic-only, contrary to what R-001's and R-003's own text (Session 10) claimed. A live test proved it: a real operator's `pulsewatch_session` cookie — `Secure`, `HttpOnly`, issued over `https://localhost:8443` — was replayed against `http://localhost:8020/api/v1/targets` in cleartext and the backend returned real target data. `Secure` did not stop this because `localhost`/loopback is treated as a trustworthy origin by browsers/`curl` regardless of scheme; `Path`/`Domain` cookie attributes don't carry port scoping either (RFC 6265) — ruled out as non-fixes rather than tried and found wanting. | Security / Deployment | Was High while open — a replayed operator cookie returned real dashboard-scoped data (targets), not just a bearer token | Was certain — demonstrated working against the real running stack, not hypothetical | **Split the routers, not the TLS story (chosen over routing agent traffic through Caddy too — see `08-deployment-and-operations.md` for why).** `backend/main.go` now constructs two `*gin.Engine`s (`setupOperatorRouter`, `setupAgentRouter`) and runs two independent `http.Server`s: `operatorSrv` (`:8080` inside the container, every `operatorapi` route, no `agentapi` route mounted at all) and `agentSrv` (`:8081` inside the container, every `agentapi` route, no `operatorapi` route mounted at all). `docker-compose.yml` publishes only the agent listener to the host (`8020:8081`); the operator listener is reachable exclusively through the internal Docker network — by `proxy`/Caddy (R-001) or another container, never directly from the host in any scheme. This is a structural fix, not a check that happens to catch the demonstrated replay: `TestOperatorRouterHasNoAgentRoutes`/`TestAgentRouterHasNoOperatorRoutes` (`backend/main_test.go`) assert the routes are genuinely unmounted, not merely rejected. Re-verified live: the exact same minted operator cookie that returned real target data over `https://localhost:8443` gets a real `404 page not found` when replayed against `http://localhost:8020/api/v1/targets` — the route doesn't exist there, full stop. A real agent (seeded via `cmd/seed-agent`, run via `cmd/agent`) still successfully polled `GET /api/v1/agent/assignments` and reported `POST /v1/logs` against the same now-agent-only `8020`, confirming ADR-0003 traffic is unaffected. | Session 11 (2026-08-31) |
