| R-001 | `operatorSession`'s cookie is `Secure`, but no session had given the project a real TLS termination story — `docker-compose.yml` served `backend`/`frontend` over plain HTTP, so a real browser would never store the cookie. | Security / Deployment | **Genuinely mitigated, with an honestly-named residual trade-off.** Session 10 added a real, persistent `proxy` (Caddy) service to `docker-compose.yml`, terminating HTTPS at `https://localhost:8443` for the browser-facing `frontend` (which no longer publishes any plain-HTTP host port at all) and for direct `/api/*` access to `backend`. The cert is `tls internal` — Caddy's own persistent local CA, not a publicly trusted one; a real browser shows a not-trusted warning, which is the accepted, explicitly-named trade-off for this project's self-hosted/local default (see `08-deployment-and-operations.md`'s "TLS termination" section for the full writeup and the real-domain/Let's Encrypt upgrade path). Verified end-to-end this session via a real TLS handshake (`openssl x509` showing `Issuer: CN=Caddy Local Authority - ECC Intermediate`) and a full `curl` cookie-jar round trip against the actual running `docker compose up` stack: `POST /login` over `https://localhost:8443` → real `Set-Cookie: pulsewatch_session=...; HttpOnly; Secure; SameSite=Strict`; that cookie, replayed in a **separate** subsequent request (not the same connection — proving persistence across a reload, not just an in-flight assumption), rendered the real dashboard; unauthenticated `GET /dashboard` → real `303` to `/login`; `POST /dashboard?/logout` cleared the cookie (`Max-Age=0`) and a following `/dashboard` request redirected to `/login` again. Not "closed" in the sense of no residual gap at all — see R-003 for the distinct, separately-tracked agent-transport gap this does not cover. | Session 10 (2026-08-31) |
