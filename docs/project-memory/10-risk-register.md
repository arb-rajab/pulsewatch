## Closed risks

| ID | Risk | Category | Resolution | Closed date |
|---|---|---|---|---|
| R-001 | `operatorSession`'s cookie is `Secure`, but no session had given the project a real TLS termination story — `docker-compose.yml` served `backend`/`frontend` over plain HTTP, so a real browser would never store the cookie. | Security / Deployment | **Genuinely mitigated, with an honestly-named residual trade-off.** Session 10 added a real, persistent `proxy` (Caddy) service to `docker-compose.yml`, terminating HTTPS at `https://localhost:8443` for the browser-facing `frontend` (which no longer publishes any plain-HTTP host port at all) and for direct `/api/*` access to `backend`. The cert is `tls internal` — Caddy's own persistent local CA, not a publicly trusted one; a real browser shows a not-trusted warning, which is the accepted, explicitly-named trade-off for this project's self-hosted/local default (see `08-deployment-and-operations.md`'s "TLS termination" section for the full writeup and the real-domain/Let's Encrypt upgrade path). Verified end-to-end this session via a real TLS handshake (`openssl x509` showing `Issuer: CN=Caddy Local Authority - ECC Intermediate`) and a full `curl` cookie-jar round trip against the actual running `docker compose up` stack: `POST /login` over `https://localhost:8443` → real `Set-Cookie: pulsewatch_session=...; HttpOnly; Secure; SameSite=Strict`; that cookie, replayed in a **separate** subsequent request (not the same connection — proving persistence across a reload, not just an in-flight assumption), rendered the real dashboard; unauthenticated `GET /dashboard` → real `303` to `/login`; `POST /dashboard?/logout` cleared the cookie (`Max-Age=0`) and a following `/dashboard` request redirected to `/login` again. Not "closed" in the sense of no residual gap at all — see R-003/R-004 for the distinct, separately-tracked agent-transport/cross-port gaps this does not cover. | Session 10 (2026-08-31) |
| R-004 | **Found closing out Session 10, opened and closed within Session 11.** `agentapi` and `operatorapi` were registered on the *identical* `gin.Engine`/`http.Server` (`backend/main.go`'s old `setupRouter`), so R-001's TLS work never actually made the plain-HTTP agent port (`8020:8080`) agent-traffic-only, contrary to what R-001's and R-003's own text (Session 10) claimed. A live test proved it: a real operator's `pulsewatch_session` cookie — `Secure`, `HttpOnly`, issued over `https://localhost:8443` — was replayed against `http://localhost:8020/api/v1/targets` in cleartext and the backend returned real target data. `Secure` did not stop this because `localhost`/loopback is treated as a trustworthy origin by browsers/`curl` regardless of scheme; `Path`/`Domain` cookie attributes don't carry port scoping either (RFC 6265) — ruled out as non-fixes rather than tried and found wanting. | Security / Deployment | Was High while open — a replayed operator cookie returned real dashboard-scoped data (targets), not just a bearer token | Was certain — demonstrated working against the real running stack, not hypothetical | **Split the routers, not the TLS story (chosen over routing agent traffic through Caddy too — see `08-deployment-and-operations.md` for why).** `backend/main.go` now constructs two `*gin.Engine`s (`setupOperatorRouter`, `setupAgentRouter`) and runs two independent `http.Server`s: `operatorSrv` (`:8080` inside the container, every `operatorapi` route, no `agentapi` route mounted at all) and `agentSrv` (`:8081` inside the container, every `agentapi` route, no `operatorapi` route mounted at all). `docker-compose.yml` publishes only the agent listener to the host (`8020:8081`); the operator listener is reachable exclusively through the internal Docker network — by `proxy`/Caddy (R-001) or another container, never directly from the host in any scheme. This is a structural fix, not a check that happens to catch the demonstrated replay: `TestOperatorRouterHasNoAgentRoutes`/`TestAgentRouterHasNoOperatorRoutes` (`backend/main_test.go`) assert the routes are genuinely unmounted, not merely rejected. Re-verified live: the exact same minted operator cookie that returned real target data over `https://localhost:8443` gets a real `404 page not found` when replayed against `http://localhost:8020/api/v1/targets` — the route doesn't exist there, full stop. A real agent (seeded via `cmd/seed-agent`, run via `cmd/agent`) still successfully polled `GET /api/v1/agent/assignments` and reported `POST /v1/logs` against the same now-agent-only `8020`, confirming ADR-0003 traffic is unaffected. | Session 11 (2026-08-31) |
