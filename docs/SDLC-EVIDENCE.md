5. Verification & Testing, 8. Retirement & Handover — because Discovery &

deep phases), this repository does not duplicate that depth — see
`docs/project-memory/00a-ledger-confirmation.md` for the full rationale.

**Session 5 — the scheduler and leasing mechanism itself**, constructed exactly to ADR-0001 (Postgres row leasing) and ADR-0004 (bounded worker pool, context-based graceful drain) with no redesign: `backend/internal/scheduler` implements the tick loop (1s default, configurable), the 20-worker (default) long-lived pool, ADR-0001's atomic conditional claim (`UPDATE target_schedule SET lease_owner=..., lease_expires_at=... WHERE next_due_at<=now() AND (lease_expires_at IS NULL OR lease_expires_at<now()) RETURNING target_id`, unchanged in predicate/columns from the ADR — only the interval literal's parameter encoding differs to fit the pgx driver), and the same-transaction release (insert `check_results`, advance `next_due_at`, clear the lease). Basic HTTP/TCP check execution per Session 2's MVP boundary (2xx = success, optional literal-substring body-match, TCP dial success/refused/timeout) — kept deliberately simple per this session's own scope, since leasing/concurrency/restart correctness was the substance. Four properties proven, not assumed, matching this portfolio's per-repo safety-critical-mechanism standard:
- **Exclusivity under genuine concurrency** (`TestClaimLease_ExactlyOneWinnerUnderRealConcurrency`, `backend/internal/scheduler/concurrency_test.go`): 20 real, independent goroutines, each racing through its own connection out of a real `pgxpool.Pool` against a real Postgres, released at a shared start barrier to claim the identical lease. Exactly one wins every run (verified `-count=3` under `-race`). **Proven to have real teeth, not just pass by construction**: the claim was temporarily weakened to a read-then-write (SELECT lease state, decide in Go, then UPDATE — no atomic WHERE guard) and the same test then failed reliably (13–14 of 20 goroutines "won" per run, across 5 repeated runs) before the atomic implementation was restored and reverified passing.
- **Restart recovery is literally the same code path, not a special case** (`TestRestartRecovery_SameTickLogicReclaimsStaleLease` and `TestClaimLease_ReclaimsLeaseAbandonedByAnotherOwner`, `backend/internal/scheduler/restart_recovery_test.go`): a lease row is seeded with a foreign, expired owner (simulating a crash mid-check), then a fresh `Scheduler.Run` — the identical method every ordinary tick uses, with no `Recover`/`RunRecovery` function existing anywhere in the package — reclaims it, executes exactly one check, and releases cleanly with `next_due_at` advanced and no duplicate `check_results` row.
- **Graceful shutdown, both outcomes** (`backend/internal/scheduler/shutdown_test.go`): `TestGracefulShutdown_InFlightCheckFinishesNaturally` proves a check already claimed when the root context cancels is not yanked — it keeps running to completion under its own per-check timeout (detached from the canceled root context by design) and records a real result. `TestGracefulShutdown_ForceCancelAtHardDeadline_LeavesLeaseAbandonedNotCorrupted` proves the other side: a check still running at the (short, test-configured) hard shutdown deadline is force-canceled, records **no** result (never a half-processed or duplicate one), leaves the lease exactly as the claim set it (abandoned, not cleared, not corrupted), and that abandoned lease is later reclaimable via the same ordinary `claimLease` predicate once it actually expires.
- Full suite (`backend/...`, unit + all four integration tests above) passes under `go test ./... -race -v -count=3`; `golangci-lint run ./...` at the pinned CI version (`v2.13.2`) is clean (`0 issues`) including the context-propagation linters Session 4 turned on — the one intentional `context.WithCancel(context.Background())` detach point (the drain context ADR-0004 requires to outlive the root context) is `//nolint:contextcheck`-annotated with its ADR rationale, not silently suppressed. `govulncheck` found and required a real fix: `golang.org/x/text` (an indirect dependency pulled in by the newly-added `github.com/jackc/pgx/v5`) was vulnerable to GO-2026-5970, reachable through `pgxpool.New`; upgraded `v0.34.0` → `v0.39.0`, reverified `0 vulnerabilities`. Also verified against the real `docker compose up --build` stack (not only throwaway test containers): a manually inserted HTTP target (`http://backend:8080/health`) and TCP target (`redis:6379`) were both claimed, checked, and recorded (`check_results.success = true`, real status code/latency) by the running `backend` container within one tick, with the lease correctly released and `next_due_at` advanced afterward. CI (`.github/workflows/ci.yml`) reordered, not rebuilt: migrations now apply once *before* `go test` (a real, necessary fix — Session 4's tests never touched Postgres, so step order didn't matter yet; Session 5's integration tests do, and would silently fail against a schema-less database without this) in addition to the existing later up→down-all→up reversibility check. Scheduler tuning (`SCHEDULER_WORKER_POOL_SIZE`/`_TICK_INTERVAL`/`_LEASE_SAFETY_MARGIN`/`_HARD_SHUTDOWN_DEADLINE`) exposed as `docker-compose.yml`/`.env.example` environment variables matching this repo's `${VAR:-default}` pattern, per ADR-0004's explicit "configuration, not hardcoded constants" consequence. | `backend/internal/scheduler/`, `backend/main.go`, `backend/go.mod`, `.github/workflows/ci.yml`, `docker-compose.yml`, `.env.example` |
